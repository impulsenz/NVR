# GAZE audit — November 2026 (version 1.1.9 → 1.1.10)

An independent review of the code base, run in one working session. It builds
on the earlier performance audit (`ARCHITECTURE-AND-PERFORMANCE.md`, version
1.0, with benchmarks) instead of repeating it.

**How to read it.** Every claim is tagged:

| Tag | Meaning |
|---|---|
| **[measured]** | A number taken in this session, with the command that gives it |
| **[code]** | Read in the source (file named) |
| **[reasoned]** | Follows from the code, not measured |
| **[reported]**  | From a source outside the repository (named); not independently verified |

**What this audit is not.** It is not a line-by-line review of 40,000 lines, a
penetration test, or a load test with real cameras. It sampled: the
authentication and authorisation path, every route that takes a camera, the
configuration, dependencies, the build, and a running server. Where
something wasn't looked at, section L says so. Competitor research was
limited by the session's network allow-list (see H).

## A. Executive summary

**Overall health: good, with three structural weaknesses that matter more
than any single bug.**

What is solid **[measured]/[code]**:

* 130 + 11 tests passed at the baseline (133 + 11 after this session's regression tests); `cargo clippy` gives 29 style warnings and **no
  correctness or suspicious-code lints**; `cargo audit` finds **0
  vulnerabilities** in 365 locked crates (one maintenance notice, chrono).
* Recording does not depend on AI: `recorder.rs` references none of
  `ai`/`detect`/`infer` **[code]**. Video is copied, not transcoded
  (`-c:v copy`), one camera connection is shared by every consumer
  (`relay.rs`), every queue is bounded (no `unbounded_channel` anywhere), every
  ffmpeg child is `kill_on_drop`, and reconnects back off exponentially.
* Idle footprint with no cameras: **35 MB resident, 5 threads, 0.4 % CPU**
  (debug build) **[measured]**.
* Settings are tidy: of **260** settings only **1** is mentioned nowhere
  outside `config.rs` (a legacy migration field) **[measured]**
  (`tools/audit/config_usage.py`). All **35** direct dependencies are used.
* Passwords are Argon2, sessions are HttpOnly SameSite cookies with a
  separate Secure cookie on https, state-changing requests from other origins
  are refused (also WebSocket upgrades), API tokens are scoped to their owner,
  sign-in locks out with growing waits.

The three structural weaknesses:

1. **Camera authorisation is enforced by convention.** A restricted account is
   kept off other cameras by a path check in one middleware plus **35
   individual handler checks**. Anything the middleware doesn't recognise
   depends on someone remembering to add a check. Frigate shipped fixes for
   this exact class twice this year ("cross-camera auth in timeline and media
   endpoints", 0.17.1 **[reported]**). I found two gaps (S1, S2) — both fixed
   here, with tests — and the design that allows them remains (action H-1).
2. **One panic can cascade.** 292 `lock().unwrap()` calls on `std::sync::Mutex`
   mean a thread that panics while holding a lock poisons it, and every later
   caller panics too **[code]**. A fault in one subsystem can therefore reach
   others. (H-2.)
3. **Layered, drifting front end.** `app.js` is one 9,800-line file with 38
   timers; `app.css` defines **84 selectors more than once**, the timeline
   three or four times **[measured]**. That drift produced a real bug this
   month: a later "redesign" of the timeline hard-coded dark colours over the
   earlier rules that followed the theme, so the day theme had a black
   timeline (fixed in 1.1.9).

Nothing found is a **critical** (data loss, remotely exploitable) issue.

Changes made in this session are in **K**; what was left, and why, in **L**.

## B. Architecture assessment

Full map: `ARCHITECTURE.md`. In one paragraph: GAZE is one Rust program (axum
+ Tokio) that supervises ffmpeg processes, a plain-JavaScript page served from
the binary, two optional helper programs (the watchdog, and go2rtc), and files
on disk. There is **no database**: settings are TOML, alerts are JSON lines per
camera held in memory, recordings are found by listing folders (cached 5 s),
cases are one JSON file.

**What the design gets right**

* *One connection per camera stream, many local consumers.* Cameras that
  limit sessions (most do) are not overloaded, and a failing consumer can't
  take the others down. Cost: ~5 ffmpeg processes per camera (measured in the
  1.0 audit: 20 for 4 cameras).
* *Passthrough everywhere it can be*: recording, live MSE video. Decoding
  happens once, on the sub-stream, for motion/AI and the JPEG grid.
* *Independence of AI*: AI and recording are separate tasks; AI failure
  degrades alerts only.
* *Verified moves/copies* (`cloud::copy_local`: size + SHA-256, `.partial`,
  fsync, rename), crash repair (`mp4fix.rs`), safe mode for a broken settings
  file.

**Weaknesses**

| # | Where | Issue | Why it matters |
|---|---|---|---|
| AR-1 | `web.rs` (6,500 lines) | Routes, auth middleware, HLS, cases, archive, watchdog, settings, status in one file | Hard to review; authorisation rules are spread through it (see S1) |
| AR-2 | 72 global `static` Mutex/LazyLock/OnceLock | Hidden shared state (snooze, jobs, cloud status, archive status, registries…) | Hard to test; order-of-init bugs |
| AR-3 | `events.rs` `between()` | Linear scan + clone of every event in range, called per timeline request and by the 8 s alert refresh **[code]** | Fine today; grows with alert retention. **Not measured** — benchmark before changing (the 1.0 audit measured folder listing, not events) |
| AR-4 | `app.js`, `app.css` | Single files, no modules, no tests | Regressions found by users (flicker, theme) |
| AR-5 | Two "NAS" features | *Backup* (copy, `cloud.rs`) and *Deep storage* (move, `archive.rs`) overlap in purpose and UI | Users must understand the difference; both are legitimate (copy vs tier) but the page names don't say so |
| AR-6 | Windows-only code (service, tray, watchdog) | Compiles only on the Windows CI runner | Breaks are found at release time (see the CI gate, H-3). A Linux→Windows cross-check **works** (`x86_64-pc-windows-gnu` + mingw) and is now documented |

## E. Security assessment

**Verified good [code]:** Argon2 password hashes; random session tokens kept
across restarts; `HttpOnly; SameSite=Lax` cookie, plus a separate `Secure`
cookie on https; origin check on every request including WebSocket upgrades
(blocks cross-site WebSocket hijacking and most CSRF); `X-Frame-Options: DENY`,
`nosniff`, `Referrer-Policy: same-origin`; per-role allow-list (`allowed()`);
API tokens removable only by their owner; signed, expiring snooze links;
camera passwords masked in API output (`mask_url`); every external process is
started with an argument *list* (no shell strings); recordings, cases and
archive files are looked up by validated names (`valid_component`,
`resolve`) — no path traversal found in the routes sampled; zip export names
are sanitised.

| ID | Severity | Finding | Status |
|---|---|---|---|
| **S1** | Medium | Central camera check (`camera_in_path`) did not recognise `/api/hls/{id}/…` and `/api/hls-file/{id}/…`. The handlers did check, so nothing was exploitable, but a future handler on those shapes would have been open | **Fixed** (added; regression test lists every camera path shape) |
| **S2** | Medium | Evidence Locker: changing or removing an item, and renaming/deleting a case, did **not** check camera visibility. An *operator* restricted to some cameras could edit notes/protection of, or delete, items from cameras they cannot see | **Fixed**, handlers refuse (`case_hidden_from`, `case_item_hidden_from`) |
| **S3** | Low–Medium | Camera addresses accepted any scheme. ffmpeg and go2rtc read `file:`, `exec:`, `pipe:` …; an address pre-filled from what a LAN device reports during discovery could reach them. Admin-only today (an admin can already set the ffmpeg path), so this is defence in depth against *untrusted devices*, not privilege escalation. Frigate had a go2rtc `exec` bypass advisory in 0.18.2 **[reported]** | **Fixed**: streaming-scheme allowlist on add/change/test/preview and in go2rtc config; settings files already saved still load |
| S4 | Low–Medium | No `Content-Security-Policy`, `Strict-Transport-Security` or `Permissions-Policy`. The page is built with large `innerHTML` templates and inline `onclick` handlers, so a strict CSP needs a refactor. A scan of 9,800 lines for unescaped interpolations flagged 59 candidates; the 12 sampled were all text contexts (toasts, titles), none HTML | Open (H-4) |
| S5 | Low | `GET /api/snooze` changes state without a session (HMAC-signed link, 2-day expiry, built for notification buttons). Whether the signature comparison is constant-time was **not verified** | Open: check `notify::snooze_ok` |
| S6 | Info | `danger_accept_invalid_certs` appears only for an explicitly trusted remote GAZE (`trust_own_cert`) and the watchdog's check of GAZE on this computer | Accepted |
| S7 | Info | Camera passwords are stored in the settings file (mode-restricted by `config::private_file`), as in every NVR that must log in to cameras. Not encrypted at rest | Accepted; note for backups (the export asks before including secrets) |
| S8 | Not assessed | Brute-force lockout is per user (`users.rs`); whether it also limits by address was not checked | Open |

Dependency risk: `cargo audit` clean; one *unmaintained* notice for `chrono`
(RUSTSEC-2026-0543, dated 2026-09-14 **[reported by the RustSec database]**).
chrono is used throughout; migrating is a large change with no current
vulnerability — tracked, not urgent. The model files for description search
are downloaded with **pinned SHA-256** (`clip.rs`) — good supply-chain practice;
the same pinning should apply to other downloads (ffmpeg, go2rtc, voices): not
checked.

## F. Performance assessment

Prior measurements (1.0 audit, simulated cameras) stand: shared live
repackaging, no per-viewer ffmpeg growth, bounded queues. New in this audit:

| # | Finding | Evidence | Status |
|---|---|---|---|
| P-1 | **The page was sent uncompressed and re-sent in full on every load.** `app.js` 735,157 B, `app.css` 137,104 B, `index.html` 31,390 B served with `Cache-Control: no-cache` and no validator, even to browsers that accept gzip | **[measured]** `curl` against a running server | **Fixed**: gzip once at start-up, ETag, 304 |
| | Cold load | **903,651 B → 259,196 B (−71 %)** (8,795 + 221,043 + 29,358) | |
| | Reload | three `304` responses, 0 B bodies (was ~900 KB) | |
| | `hls.min.js` (Recordings) | 415,253 B → 125,023 B | |
| P-2 | `/api/status` (polled every 2 s per open tab) and other JSON are uncompressed | **[code]** | Open. Size depends on camera count (not measured here, no cameras). Compress JSON with a *type-limited* layer: a blanket compression layer would break MJPEG/MP4/WebSocket streams |

| P-4 | ~5 ffmpeg processes per camera | 1.0 audit | Already weighed there; merging them trades isolation for processes. Left |

option). No change recommended without measurements on real cameras.

## G. AI assessment

**[code]** Built-in YOLOX (nano → large) through ONNX Runtime with DirectML on
Windows, tract on CPU; models downloaded on demand; a "double-check in HD"
second pass; stationary-object suppression; zones and lines; faces and plates
(`recog.rs`, `identify.rs`) run after an alert ends on an HD picture; CLIP
ViT-B/32 (English, 420 MB, pinned hashes) for search by description
(`clip.rs`); YAMNet-class sound detection. AI backs off when the CPU is
busy (`load.rs`). Recording never waits for AI.

Assessment:

* The structure is right: AI is optional, local, scheduled, and isolated from
  recording. Nothing found that should be removed.
* The CLIP index is the most capable feature relative to cost: Frigate's
  semantic search needs 8 GB RAM minimum and recommends a GPU **[reported by
  Frigate's docs]**; GAZE's ViT-B/32 is smaller.
* Not evaluated (needs hardware): TensorRT/OpenVINO, batching across
  cameras, re-identification models, a local vision-language model.

## I. Innovation proposals

Ranked by value/cost for GAZE specifically. None is built yet.

1. **Saved searches that alert ("triggers")** — reuse the existing CLIP
   index: a saved description ("a person carrying a ladder") becomes an alert
   rule with a similarity threshold. Needs: an index query on each new alert,
   one setting. Low cost, genuinely new for users. Frigate reports that
   text→image thresholds are unreliable (CLIP scores cluster), so offer
   *image* examples (pick an alert picture) as the trigger — their recommended
   form.
2. **Image→image search** ("find more like this alert") — the same CLIP
   vision model, no new download.
3. **Verified "evidence package" for sharing** — the Evidence Locker export
   already includes a SHA-256 manifest; add a signed (HMAC) manifest and an
   optional "viewer link" with expiry. Differentiator for the insurance/police
   use case.
4. **Self-diagnosing health page** — the watchdog, deep-storage status, disk
   and camera errors already exist in separate places; one "Is everything OK?"
   card with a plain verdict.
5. **Opt-in local LLM summaries** (Ollama endpoint, user-supplied) of an
   alert's picture series — only after 1 and 2, and only local.
6. **Test harness with synthetic cameras in CI** (the 1.0 `tools/bench`
   already exists): a nightly job that records 4 simulated cameras for 10
   minutes and checks no ffmpeg leak, no growth in memory.

If building from scratch: keep the one-connection relay; consider SQLite *only*
when embeddings or cross-camera queries arrive (the 1.0 audit measured the
folder listing at 16 ms and rejected it; that reasoning holds); split the web
layer by feature; give the page real modules and a component test run.

## L. Remaining technical debt, and why it was left

See `TECH-DEBT.md` for the live register. Deliberately not done, and why:

* **H-1/H-2/H-4 and the large refactors** — each touches many files and
  needs review; doing them blind in one session would add risk to a recording
  product. They are specified above with their tests.
* **No SQL database** — measured argument from the 1.0 audit still holds.
* **No new AI models / TensorRT / OpenVINO** — no GPU or benchmark data here.
* **Not examined:** the ONVIF device proxy (`onvif_device.rs`, 935 lines) for
  input handling; per-address brute-force limits (S8); checksum pinning of
  the ffmpeg/go2rtc downloads; the remote-GAZE import (`remote.rs`) trust
  model; real-camera behaviour under power cuts (the repair code has tests,
  but no power-cut test was run).
* **`cargo fmt`**: 850 formatting differences — the code isn't rustfmt-style
  (very wide lines). A mass reformat would bury `git blame`; no format gate is
  enforced.
* **Skills / MCP servers**: none installed. No relevant skill exists in the
  directory, and the only security-related connector offered is a hosted
  service that would receive source code. Tooling used and recommended is in
  `TOOLING.md`.
